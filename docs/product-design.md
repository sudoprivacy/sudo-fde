# 生产产品形态

## 两个入口

业务端入口是 `/`。未登录用户进入普通登录页；登录后只看到自己所属租户和被授权的工作区。业务端包含工作区、资料与知识库、我的模型、组织成员、模型与用量、审计（按角色显示）。普通用户不会看到平台内部服务地址、模拟器、开发标识或跨租户数据。

平台管理端入口是 `/admin`。只有 `platform_admin=true` 的平台管理员可进入。它使用相同的安全会话，但采用独立控制台布局和 API 边界，提供：

- 平台总览：租户、用户、工作区、任务、失败率及组织/个人模型调用；
- 租户管理：新建、查看、编辑、停用、软删除与恢复、成员/工作区数量、Router 绑定状态；
- 用户管理：跨租户用户、关联租户与调整角色、账号停用/恢复、授予平台管理员；
- 任务与模型：按租户查看后台任务、模型、错误和状态；
- 全局审计：跨租户组织、权限、资料、模型和任务事件，支持访问记录过滤和分页。

平台管理员权限只在后台接口判定；导航按钮只是可见性优化。PostgreSQL RLS 通过 `app.platform_admin` 扩展为受控的全局管理上下文，必须由服务端会话产生，不能从请求体或浏览器字段设置。

## 用户权限

用户登录后由成员关系获得当前租户角色：组织所有者、组织管理员、FDE 成员、账务查看者。工作区另外有拥有者、编辑者和查看者。知识库可以绑定租户、工作区、用户、角色或工作区授权。停用用户、移除成员、停用知识库或撤销文档后，读取、检索、任务提交、任务完成和导出下载都会再次校验。

普通账号仅能列出自己有效关联的组织，切换组织也须验证有效成员资格；不能通过旧的新建组织接口自行扩展租户范围。组织所有者和组织管理员在「组织设置」中修改当前组织名称，并管理本组织成员；请求不能指定其他租户或授予平台权限。跨租户的租户、用户、任务和审计管理仅开放给服务端记录的 `platform_admin`。初始化的 admin 账号明确拥有这一权限，账号名称或邮箱本身不构成授权。

组织名称在全平台唯一，包括停用的组织。注册、新建和改名统一去除首尾空白、合并连续空白、转换全角英数字，并通过数据库唯一索引忽略英文大小写。重名返回明确提示。迁移 `0006` 保留已有主要工作区所在组织的名称，为其他同名组织增加序号，不合并成员或工作区；名称调整新增审计记录。

审计列表显示租户名称、中文操作、操作人姓名和邮箱、资源名称以及中文变更详情。历史资源已不存在时显示名称不可用；原始事件代码、编号和参数放在可展开的技术详情中，原始审计记录不作修改。业务端与管理端使用相同展示规则，名称解析保持租户隔离。名称取当前资源信息，事件原始变更参数单独保留。

## 用户模型配置

「我的模型」允许个人配置一个或多个模型提供商：Provider ID、显示名称、API 地址、OpenAI/Anthropic 协议、API Key、模型目录和默认模型。填写地址和 API Key 后可以读取提供商的 `/models` 目录，在搜索、全选/取消全选的弹窗中选择要加入的模型。已添加的模型按行展示，支持搜索、逐条移除、手动添加，以及通过行内按钮或下拉框切换默认模型。移除默认项时选择剩余模型作为替代；目录为空时不能保存。修改保存后生效，提供商卡片展示默认模型和目录摘要。API Key 使用 Fernet 密钥加密保存，响应只返回“已配置”状态；删除时立即软停用并替换密文。生产地址必须使用 HTTPS，不能带用户名、密码、查询参数或本机地址。

工作区任务的模型选择包含组织 Router 模型和当前用户的个人模型。个人模型走 `UserProviderLLM` 的受控协议适配；组织 Router 模型继续走预占、执行、结算和对账合同。任务会保存 provider_id、模型、流水线版本和引用快照，历史任务不会因为用户编辑提供商而换模型。后续接入 SudoRouter 用户 API Key 时只需把提供商的 API 地址和认证适配替换为 Router 的授权出口，任务接口不变。

首次保存资料自动生成概要与手动运行能力使用同一模型选择，提交时均携带 `provider_id` 和 `model`。个人提供商不要求绑定组织 Router。选择按用户、租户和工作区记忆，在任务轮询与页面重新渲染时保留。组织未绑定时不展示其候选模型；已知的图像、语音和向量专用模型不参与业务分析选择，提供商默认模型不适用时使用目录中的首个对话候选。未知的自定义模型仍允许使用，其实际能力由提供商决定。

旧客户端未传模型选择时，先尝试已绑定的组织模型，否则只查找当前用户在当前租户中的个人提供商。自动 AI 启动被拒绝时保留已提交的资料，返回明确的启动失败原因，用户可选好模型后手动运行“业务概要”。个人提供商被撤销或模型从目录移除后，未执行的任务也会重新校验权限。

## AI 业务流程

新建工作区时设置“这次希望解决什么问题”。第一次提交业务资料可以显式启动概要任务；后台自动进入业务概要阶段。之后状态机依次经过：

1. 业务概要：提炼一句话概要、经营范围、客户、价值链和待确认点；
2. 挑战与目标：回答业务挑战、具体问题和希望先解决的目标；
3. 接入业务资料：上传 DDL/元数据目录和专业文档，异步解析和索引；
4. 访谈与对齐：结合原话、结构目录和授权知识继续追问；
5. 理解与本体：生成业务问题、流程、系统、本体和 Agent 建议；
6. 细化与交付：字段绑定、指标粒度、缺口/线下步骤、可回答性和交付包。

每个阶段都由持久化 Job 驱动，页面显示状态、下一步和错误恢复。任务受工作区版本和流水线版本保护：资料或确认状态变化时旧任务不会发布过期结果；模型重试保持中间产物 ID 稳定，避免重复扣费或重复卡片。人工接受、修改、驳回形成不可变裁决，修订先预览后应用并可撤销。

## 生产生命周期

注册或邀请 → 组织成员授权 → 创建工作区 → 设置目标 → 提交资料触发概要 → 挑战回答 → 上传目录/知识 → 追问和对齐 → 结果裁决 → 业务细化 → 生成 YAML/OWL/BPMN/R2RML 交付包 → 持续修订与审计。平台管理员处理租户和全局运营；业务成员不接触平台级数据。
